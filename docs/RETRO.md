# 팀 회고

1. 에이전트가 가장 도움이 된 순간은 언제였나요? (구체적 사례)
- 장바구니(M1)에서 에이전트가 계획을 먼저 보여 주고, 계약서에 없는 경우(STOPPED 상품 표시, 합산 수량 99 초과)를 추측하지 않고 질문해 줬다. 덕분에 사람이 기준을 정하고 PLAN.md 가정에 남길 수 있었다.
- [팀원이 M2~M5에서 도움이 된 순간 추가]

2. 에이전트가 틀렸거나 방향을 잃은 순간은? 우리는 어떻게 알아챘고 어떻게 바로잡았나요?
- changeQuantity 계획에서 details.maxAddable 값을 에이전트가 처음엔 재고 기준(max(0, stock))으로 냈다. 내가 계약서 문구만 보고 틀렸다고 판단해 다시 계획을 받았는데, 두 번째 계획은 "재고 − 현재 수량"으로 바뀌었고 설명(테스트가 3을 기대)과 계산(3−1=2)이 맞지 않았다. 테스트 숫자(재고 3, 담긴 수량 1, 요청 4 → maxAddable 3)를 직접 계산해서 잘못을 알아챘고, 첫 번째 계획이 맞다고 판단해 되돌렸다. 구현 후 npm run test:m1을 직접 실행해 통과를 확인했다.
- addToCart 계획에는 maxAddable 계산이 빠져 있어서 승인할 때 "재고 − 기존 수량, 0 미만이면 0"을 명시했다.
- [팀원이 M2~M5에서 틀렸던 순간 추가]

3. 계획 · 작은 단위 · 테스트 먼저 · diff 리뷰 중, 우리 팀에서 가장 효과가 컸던 습관은?
- 함수 하나씩 계획을 먼저 받고 사람이 계약서·테스트와 대조한 뒤 승인한 것이 가장 컸다. 에이전트가 틀린 계획을 낸 순간(changeQuantity)을 구현 전에 잡을 수 있었다. 또 에이전트의 "통과한다"는 말을 믿지 않고 npm run test:m1을 직접 실행해 확인한 것도 효과적이었다.
- [팀원 의견 추가]

4. AGENTS.md(규칙 파일)에 실습 중에 추가하거나 고친 규칙이 있다면?
- Mission 0에서 TODO 3줄을 팀 규칙으로 채우고 TODO 표시를 제거했다(커밋 형식과 테스트 확인 후 커밋, diff는 검증자가 읽기 전 수락 금지, 에이전트의 "통과" 말은 증거로 인정하지 않음).
- 실습 중 추가한 규칙: [있으면 적기, 없으면 "없음"]

5. 다음에 AI 에이전트와 일할 때 바꿀 점 한 가지는?
- 값을 계산하는 규칙(maxAddable 등)은 계획 승인 전에 테스트의 숫자로 직접 계산해 보고, 요청문에 계산 공식과 예시 숫자를 넣는다.

6. (선택) 이 실습의 문제 · 계약서에서 모호했던 부분은?
- 담긴 상품이 STOPPED가 됐을 때 getCart의 동작, 합산 수량이 99를 넘을 때의 처리가 계약서에 없었다.
- changeQuantity의 maxAddable("지금 더 담을 수 있는 최대 수량")이 수량을 교체하는 함수에서 무엇을 뜻하는지 모호했다. 공개 테스트로 재고 기준임을 확인했다.
