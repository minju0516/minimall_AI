# 팀 회고

### 1. 에이전트가 가장 도움이 된 순간은 언제였나요? (구체적 사례)

- M1에서 에이전트가 계획을 먼저 제시하고, 계약서에 없는 동작(STOPPED 상품 표시, 합산 수량 99 초과)에 대해 추측하지 않고 질문한 점이 도움이 됐다. 사람이 기준을 정하고 PLAN.md에 가정을 남길 수 있었다.
- M2~M4에서는 함수와 규칙을 작은 단위로 나누어 구현하고 단계별 테스트를 실행하면서 기능을 점진적으로 완성할 수 있었다. 특히 주문 생성, 결제, 주문 취소처럼 여러 조건이 필요한 기능을 순서대로 구현하는 데 도움이 됐다.
- M5에서는 에이전트가 코드 리뷰를 통해 결함을 찾고, 결함별 재현 테스트를 작성한 뒤 수정하는 과정을 지원했다. 테스트 결과를 통해 결함 수정 여부를 확인할 수 있었다.

### 2. 에이전트가 틀렸거나 방향을 잃은 순간은? 우리는 어떻게 알아챘고 어떻게 바로잡았나요?

- M1의 changeQuantity 계획에서 details.maxAddable 값을 처음에는 재고 기준(max(0, stock))으로 제안했다. 두 번째 계획에서는 "재고 − 현재 수량"으로 바뀌었지만, 설명은 테스트가 3을 기대한다고 하면서 계산은 3−1=2로 서로 맞지 않았다. 테스트 숫자를 직접 계산해 잘못을 알아챘고, 첫 번째 계획이 맞다고 판단해 되돌렸다.
- M1의 addToCart 계획에는 maxAddable 계산이 빠져 있어, 사람이 승인할 때 계산 기준을 명시했다.
- M2에서는 에이전트가 처음에 함수 3개를 한 번에 제공해 한 번에 함수 하나만 구현한다는 규칙을 어겼다. 팀에서 이를 지적하고 함수 단위로 다시 진행했다.
- M5에서는 정렬 결함을 수정했는데도 테스트가 바로 통과하지 않았다. 페이지 시작 위치 결함이 정렬 결과를 가리고 있다는 점을 확인했고, 해당 결함을 수정한 뒤 두 테스트가 모두 통과했다.

### 3. 계획 · 작은 단위 · 테스트 먼저 · diff 리뷰 중, 우리 팀에서 가장 효과가 컸던 습관은?

- 함수나 규칙 묶음별로 계획을 먼저 받고 사람이 계약서 및 테스트와 대조한 뒤 승인하는 방식이 가장 효과적이었다. 에이전트의 잘못된 계획을 구현 전에 발견할 수 있었다.
- 기능을 작은 단위로 나누어 구현하고, 각 단계에서 테스트를 실행해 실패 원인을 확인한 것도 도움이 됐다.
- 에이전트가 테스트를 통과했다고 말하는 것만 믿지 않고 팀 컴퓨터에서 직접 npm 테스트를 실행해 결과를 확인했다.
- 코드 변경 내용을 사람이 직접 검토하고, 수정 가능한 파일과 금지된 파일을 확인하는 과정도 불필요한 변경을 방지하는 데 중요했다.

### 4. AGENTS.md(규칙 파일)에 실습 중에 추가하거나 고친 규칙이 있다면?

- Mission 0에서 TODO 3줄을 팀 규칙으로 채우고 TODO 표시를 제거했다.
- 채운 규칙은 미션별 커밋 형식을 지키고 테스트 확인 후 커밋하기, 검증자가 diff를 읽기 전에는 수락하지 않기, 에이전트의 "통과할 것"이라는 말은 증거로 인정하지 않기이다.
- 실습 중 AGENTS.md에 새로 추가한 규칙은 없다. 대신 기존 규칙(한 번에 하나의 함수, 계획 승인 후 구현, 테스트 결과는 사람이 직접 확인)을 지켰고, 계약서에 없는 동작은 에이전트가 추측하게 두지 않고 사람이 정해 docs/PLAN.md의 가정에 기록했다.

### 5. 다음에 AI 에이전트와 일할 때 바꿀 점 한 가지는?

- 값을 계산하는 규칙(maxAddable 등)은 계획 승인 전에 테스트의 숫자로 직접 계산해 보고, 요청문에 계산 공식과 예시 숫자를 넣는다. 또한 한 번에 하나의 작업 단위만 구현하도록 하고, 계획 승인과 테스트 검증을 반드시 거치도록 한다.

### 6. (선택) 이 실습의 문제 · 계약서에서 모호했던 부분은?

- M1에서 담긴 상품이 STOPPED 상태가 됐을 때 getCart의 동작과 합산 수량이 99를 넘을 때의 처리가 계약서에 명확히 정의되어 있지 않았다.
- changeQuantity의 maxAddable이 수량을 교체하는 함수에서 무엇을 의미하는지 모호했다. 공개 테스트의 기대값을 확인해 재고 기준임을 판단했다.
- M5에서는 정렬 결함과 페이지 시작 위치 결함이 서로 영향을 주어, 한 결함을 수정해도 테스트가 바로 통과하지 않는 문제가 있었다. 결함별 재현 테스트가 가능한 한 하나의 결함만 검증하도록 작성할 필요가 있었다.
